# מקרי קצה בהשוואת נתונים — CompareD

תאריך: 2026-09-07 · נבדק על בסיס: `Services/CompareService.cs`, `Services/CsvParser.cs`

## איך נבדק

לא ניחשתי מהקוד. בניתי פרויקט בדיקה שמפנה ל-`CompareD.dll` שנבנה, וקורא
בעזרת reflection למתודות האמיתיות — `NormalizeTypedValue`, `BuildCompositeValue`,
`EscapeKeyPart`, `CsvParser.ParseLine` ו-`CsvParser.Parse`. כל ממצא שמסומן
**נבדק בהרצה** מגיע עם הפלט שהתקבל. ממצא שמסומן **מקריאת קוד** הוא הסקה
מהקוד שלא הרצתי, וצריך להיקרא כהשערה מבוססת ולא כעובדה.

הבדיקה גם מנעה דיווח שגוי אחד: בנתיב ה-Concat של `BuildCompositeValue` הקוד
נראה בפלט טרמינל כמו `string.Join("", ...)`, אבל בבייטים של הקובץ הוא
`string.Join("\x01", ...)` — תו בקרה U+0001 ממשי שאינו נראה. המפריד קיים,
ההרצה הוכיחה שהחלקים אכן מופרדים, והמימוש נכון. הערה קטנה בלבד: תו בקרה
מוטבע בקוד המקור שביר — עורך, מיזוג או העברה בין מערכות עלולים לאכול אותו,
ואז ההגנה נעלמת בשקט. עדיף `""` כ-escape מפורש שעושה בדיוק אותו דבר
אך שורד כל טיפול בטקסט.

## מה כבר מכוסה טוב

זה נבדק והתנהג נכון, כדי שיהיה ברור שאני לא מציע להחליף מה שעובד:

| מקרה | תוצאה |
|---|---|
| אפסים מובילים: `"012345678"` מול `"12345678"` | תואם |
| הפרשי scale: `"48.00"` מול `"48"` | תואם |
| מפריד אלפים: `"1,234.56"` מול `"1234.56"` | תואם |
| `decimal` אמיתי מול טקסט: `48.5m` מול `"48.5"` | תואם |
| NBSP בקצה הערך | מנוקה, תואם |
| פסיק בתוך שדה מוקף גרשיים ב-CSV | מפורק נכון |
| מפתח מורכב עם `|` בערך | `EscapeKeyPart` מונע התנגשות |
| הרכבת Concat של מספר עמודות | מופרד בתו בקרה, אין התנגשות |
| `DateParts` עם ריפוד אפסים ושנה דו-ספרתית | מטופל |
| `ORDER BY` על שדות המפתח לפני `TOP`/`FETCH` | קיים, עם הסבר בקוד |
| ספירת מפתחות כפולים | נספרת ומדווחת |

הרשימה הזו ארוכה, וזה אומר שהחשיבה על מקרי קצה כאן אמיתית. מה שלמטה הוא
מה שנשאר.

## 1. ערך `DateTime` אמיתי אינו עובר נרמול תאריך כלל — הממצא המשמעותי ביותר

**נבדק בהרצה.**

```
CurrentCulture = he-IL
DateTime(2026-09-13) vs "2026-09-13" (Date)   | "13/09/2026 00:00:00" | "20260913" | DIFFERENT
DateTime(2026-09-13) vs "20260913"   (Date)   | "13/09/2026 00:00:00" | "20260913" | DIFFERENT
```

**מה קורה:** `NormalizeTypedValue` מתחיל ב-`raw.ToString()?.Trim()`
(`CompareService.cs:1141`). עבור `DateTime` זו המרה **תלוית תרבות** — תחת
he-IL היא מחזירה `13/09/2026 00:00:00`. אחר כך השורה
`DateTime.TryParse(text, CultureInfo.InvariantCulture, DateTimeStyles.None, out var date)`
(`CompareService.cs:1163`) מנסה לפרסר את המחרוזת הזו **בתרבות invariant**,
שמצפה ל-`M/d/yyyy`. `13` אינו חודש חוקי, הפירסור נכשל, ובדיקת שמונה הספרות
שאחריו גם נכשלת — ולכן הפונקציה מחזירה את המחרוזת התלוית-תרבות כמו שהיא.

**למה זה חשוב:** `DateTime` הוא בדיוק מה ששתי השכבות מחזירות בפועל —
`SqlDataReader` עבור `DATETIME`/`DATE`, `OracleDataReader` עבור `DATE`,
ו-MiniExcel עבור תא תאריך באקסל. כלומר נרמול התאריך, שהוא כל הרעיון של
`kind = "Date"`, **אינו מופעל על אף תאריך אמיתי**. השוואת מסד מול מסד עובדת
רק במקרה, מפני ששני הצדדים מייצרים את אותה מחרוזת תלוית-תרבות. השוואת מסד
מול קובץ CSV שבו התאריך כתוב `2026-09-13` **לא תתאים אף פעם** — כל שורה
תדווח כפער. וברגע שהשרת יעלה עם `CurrentCulture` אחרת (למשל
`InvariantGlobalization` או locale שונה בשרת הייצור), התוצאות משתנות בלי
שדבר בקוד השתנה.

**תיקון:** לבדוק טיפוס לפני שנוגעים ב-`ToString()`:

```csharp
if (kind == "Date")
{
    // ערך תאריך אמיתי מפורמט ישירות, בלי מעבר דרך מחרוזת תלוית תרבות
    if (raw is DateTime dt) return dt.ToString("yyyyMMdd", CultureInfo.InvariantCulture);
    if (raw is DateTimeOffset dto) return dto.ToString("yyyyMMdd", CultureInfo.InvariantCulture);
    // ... ורק אחר כך המסלול הטקסטואלי הקיים
}
```

ואותו טיפול ב-`kind == "Number"` עבור `decimal`, `double`, `float`, `int`,
`long`, `short` ו-`byte` — כדי שגם שם לא נסתמך על עיגול והפרדה תלויי תרבות.
בנוסף כדאי להוסיף ל-`TryParse` הטקסטואלי את `DateTimeStyles.AllowWhiteSpaces`
ולתמוך במפורש בפורמטים הנפוצים אצלנו (`dd/MM/yyyy`, `yyyy-MM-dd`,
`dd.MM.yyyy`) דרך `TryParseExact` עם מערך פורמטים.

## 2. שדות מפתח אינם עוברים את הנרמול שהערכים עוברים

**מקריאת קוד** — `CompareService.cs:1381` ו-`1401`:

```csharp
var keyParts = keys.Select(k => EscapeKeyPart(row.TryGetValue(k.SqlField, out var v)
    ? v?.ToString()?.Trim() ?? "NULL" : "NULL"));
```

**מה קורה:** בניית המפתח המורכב משתמשת ב-`ToString().Trim()` גולמי, בעוד
שהשוואת הערכים עוברת דרך `NormalizeTypedValue` עם הטיפוס. כלומר כל
הנרמול שהושקעה בו עבודה — אפסים מובילים, הפרשי scale, פורמט תאריך —
**אינו חל על המפתח**.

**למה זה חשוב:** זה יוצר את סוג הפער המטעה ביותר בדוח. שורה עם מפתח
`INT 48` בצד אחד ו-`NUMBER(10,2) 48.00` בצד השני תדווח כ"חסרה בשני
הצדדים" — פעם כחסרה במקור ופעם כחסרה ביעד — למרות שהיא אותה שורה בדיוק
ושאר הערכים בה זהים. אותו דבר עבור מפתח `VARCHAR '007'` מול `NUMBER 7`,
ועבור `'ABC'` מול `'abc'`. במיגרציה מ-SQL Server לאורקל, שינוי טיפוס של
עמודת מפתח הוא בדיוק מה שקורה, ולכן זה לא מקרה תיאורטי.

**תיקון:** להעביר את בניית המפתח דרך אותו `NormalizeTypedValue` עם הטיפוס
של עמודת המפתח, לפני `EscapeKeyPart`. זה גם מייצר עקביות: מה שנחשב "אותו
ערך" בהשוואה ייחשב "אותו מפתח" בהתאמה.

## 3. שורה מוקפת גרשיים עם ירידת שורה הורסת את יישור כל הקובץ

**נבדק בהרצה.** קלט של שתי רשומות שבו לרשומה הראשונה יש הערה עם ירידת שורה:

```
  row 1: id="1", remark="line one", amount=""
  row 2: id="line two,100", remark="", amount=""
  row 3: id="2", remark="ok", amount="200"
  => produced 3 rows from a 2-record file
```

**מה קורה:** `CsvParser.Parse` קורא `reader.ReadLine()` (`CsvParser.cs:22`),
כלומר עובד ברזולוציית שורה פיזית ולא ברזולוציית רשומת CSV. שדה מוקף
גרשיים שמכיל `\n` — התקן מתיר את זה, ו-Excel מייצר את זה בכל שדה הערות
חופשי — נשבר לשתי שורות. השורה השנייה מתפרשת כרשומה חדשה, `amount` נעלם,
והערך `line two,100` נכנס לעמודת `id`.

**למה זה חשוב:** זה הממצא המסוכן ביותר ב-CSV, מפני שהוא **אינו נכשל** —
הוא מייצר בשקט שורות זבל שנראות כמו נתונים. הדוח יראה שורה חסרה, שורה
עודפת, ופערי ערכים בשורות שאין בהן שום בעיה.

**תיקון:** לקרוא רשומות ולא שורות — לצרוך תו-תו ולסגור רשומה רק כשמצב
`inQuotes` כבוי. לחלופין להחליף את הפרסר ב-`CsvHelper`, שמטפל בזה ובסעיף
4 יחד. ההחלפה מוסיפה תלות אחת ומוחקת את כל המשפחה הזו של באגים.

## 4. גרשיים מוכפלים לפי התקן נאכלים

**נבדק בהרצה.**

```
RFC4180 escaped quote      -> ["He said hi" | "42"]
quote inside unquoted field -> ["1234,56"]   (1 fields)
```

**מה קורה:** `ParseLine` מטפל בגרש כמתג בלבד — `inQuotes = !inQuotes`
(`CsvParser.cs:49`) — ואינו מוסיף אותו לפלט. לכן `"He said ""hi"""`,
שהוא הדרך התקנית לכתוב `He said "hi"`, מחזיר `He said hi` בלי הגרשיים.
גרוע מזה, בשורה השנייה גרש בודד בתוך שדה לא מוקף הפעיל את המתג וגרם
לפסיק להיבלע — שתי עמודות התמזגו לאחת.

**למה זה חשוב:** אם צד אחד הוא CSV והשני XLSX, MiniExcel שומר את
`He said "hi"` נכון ו-CSV מחזיר `He said hi` — פער ערכים שאין לו קיום
בנתונים. ומקרה הגרש הבודד מזיז עמודות, כלומר משפיע גם על שדות שאין בהם
גרש בכלל.

**תיקון:** בתוך מצב מוקף, גרש שאחריו גרש הוא גרש ספרותי; גרש שאחריו
פסיק או סוף שורה סוגר את השדה. גרש בשדה שאינו מוקף הוא תו רגיל.

## 5. קובץ CSV עם מפריד נקודה-פסיק מתפרש כעמודה אחת

**נבדק בהרצה.**

```
semicolon delimited -> ["a;b;c"]   (1 fields)
```

**מה קורה:** המפריד מקובע לפסיק (`CsvParser.cs:51`).

**למה זה חשוב:** אקסל בעברית, בהגדרות אזור ישראל, מייצר "CSV" עם מפריד
`;` כברירת מחדל. משתמש שיעשה "שמור בשם CSV" מאקסל ויעלה את הקובץ יקבל
מסך מיפוי עם עמודה אחת שנקראת `קוד;שם;סכום`. אין הודעת שגיאה שמסבירה
מה קרה, והמשתמש לא יבין למה הכלי "לא עובד".

**תיקון:** זיהוי אוטומטי של המפריד משורת הכותרות — לספור `,` מול `;`
מול `\t` ולבחור את השכיח. עם אפשרות לעקוף ידנית במסך ההעלאה. ולפחות
הודעה מפורשת כשזוהתה עמודה אחת בלבד והשורה מכילה `;`.

## 6. קובץ שאינו UTF-8 מייצר עברית משובשת

**נבדק בהרצה.** אותו קלט מקודד Windows-1255:

```
  ���="1", ��="���"
```

**מה קורה:** `new StreamReader(stream, Encoding.UTF8)` (`CsvParser.cs:15`).
הקידוד מקובע ל-UTF-8. ה-BOM אמנם מזוהה אוטומטית — ה-overload הזה מפעיל
`detectEncodingFromByteOrderMarks` — אבל קובץ Windows-1255 אין לו BOM,
ולכן הוא נקרא כ-UTF-8 ומשתבש.

**למה זה חשוב:** Windows-1255 הוא הקידוד של קובצי טקסט עבריים ממערכות
ותיקות, וזה בדיוק סוג המערכת שממנה מייצאים נתונים כדי להשוות מול היעד
החדש. שמות העמודות משתבשים, המיפוי נכשל, וכל הערכים העבריים מדווחים
כפערים.

**תיקון:** לרשום את `CodePagesEncodingProvider` בעלייה, ולנסות UTF-8
עם `decoderFallback: throw`; אם הפירוק נכשל, ליפול חזרה ל-1255. בנוסף
בורר קידוד במסך ההעלאה, שכן זיהוי אוטומטי לעולם אינו מושלם.

## 7. שמות עמודות כפולים בקובץ נבלעים בשקט

**נבדק בהרצה.** קלט `id,name,name` עם שורה `1,alpha,beta`:

```
  id="1", name="beta"   (2 columns kept)
```

**מה קורה:** `row[header] = val` (`CsvParser.cs:31`) דורס. הערך `alpha`
נעלם, והקובץ מדווח שלוש עמודות אך מחזיר שתיים.

**למה זה חשוב:** ייצוא מדוח או מ-`JOIN` מייצר בקלות שתי עמודות `ID`.
המשתמש ימפה את `name` ויקבל השוואה מול עמודה שהוא לא התכוון אליה, בלי
שום סימן לכך.

**תיקון:** לזהות כפילות בשורת הכותרות ולעצור עם הודעה מפורשת שמונה את
השמות הכפולים — או למספר אותם (`name`, `name_2`) ולהציג את זה במסך המיפוי.
עצירה עדיפה: מיפוי מול עמודה שגויה גרוע מהעלאה שנדחתה.

## 8. תווים בלתי נראים גורמים לפער שנראה זהה על המסך

**נבדק בהרצה.**

```
"1234" vs "1234"+RLM   (Text) | "1234" | "1234<RLM>"  | DIFFERENT
"AB" vs "A"+ZWSP+"B"   (Text) | "AB"   | "A<ZWSP>B"   | DIFFERENT
"1234" vs "1234"+NBSP  (Text) | "1234" | "1234"       | EQUAL
```

**מה קורה:** `Trim()` מסיר NBSP, מפני ש-`char.IsWhiteSpace` מחזיר עבורו
true. הוא **אינו** מסיר RLM (U+200F), LRM (U+200E) או ZWSP (U+200B),
שהם תווי פורמט ולא תווי רווח.

**למה זה חשוב:** זו התקלה שמבזבזת את הזמן הרב ביותר, כי הדוח מציג שני
ערכים שנראים אות באות זהים ומסמן אותם כשונים. וזה לא תרחיש מומצא בסביבה
הזו — שם התיקייה של הפרויקט עצמו הוא `‏‏CompareD`, שני תווי
RLM לפני השם. תווים כאלה נכנסים לנתונים דרך העתקה מדפדפן, ממסמך Word
או ממערכת עברית שמוסיפה סימני כיווניות.

**תיקון:** בנרמול הטקסט להסיר תווי פורמט בלתי נראים לפני ההשוואה —
לסנן תווים שה-`CharUnicodeInfo.GetUnicodeCategory` שלהם הוא `Format`,
ובנוסף להריץ `Normalize(NormalizationForm.FormC)` כדי שהרכבות Unicode
שונות של אותה אות ייראו זהות. חשוב: להציג בדוח את הערך המקורי ולהשוות
את המנורמל, כדי שהמשתמש יראה מה באמת יש בנתונים.

## 9. מפתח חסר ומפתח שהערך בו הוא הטקסט "NULL" מתמזגים

**נבדק בהרצה.**

```
missing key -> "NULL"  vs  data value "NULL"  | "NULL" | "NULL" | EQUAL
```

**מה קורה:** `?? "NULL"` (`CompareService.cs:1381,1401`) משתמש במחרוזת
`"NULL"` כסמן לערך חסר. שורה שבה עמודת המפתח מכילה בפועל את הטקסט
`NULL` מייצרת מפתח זהה.

**למה זה חשוב:** בייצוא CSV, `NULL` נכתב לעתים כטקסט מפורש. במקרה כזה
שורה עם מפתח ריק ושורה עם מפתח `"NULL"` יותאמו זו לזו, וההשוואה תדווח
פערי ערכים בין שתי שורות שאינן קשורות.

**תיקון:** סמן שאינו יכול להופיע בנתונים, באותה גישה של המפריד הקיים —
למשל `" "`. השוואת השורות הריקות עצמן היא החלטה נפרדת: האם שתי
שורות עם מפתח חסר אמורות להיחשב אותה שורה בכלל.

## 10. הפרש מספרי קטן מ-1e-10 נעלם, ומספר ארוך מדי חוזר להיות טקסט

**נבדק בהרצה.**

```
0.00000000001 vs 0.00000000002 (Number)  | "0" | "0" | EQUAL
38-digit vs same with leading zero       | DIFFERENT
"1.234,56" vs "1234.56"        (Number)  | DIFFERENT
```

**מה קורה:** שלושה דברים באותה שורת קוד (`CompareService.cs:1156`).
ראשית, `ToString("0.##########")` חותך לעשר ספרות אחרי הנקודה, ולכן
הפרש שקטן מזה מדווח כזהה. שנית, `decimal` מחזיק כ-28-29 ספרות משמעותיות,
ולכן `NUMBER(38)` של אורקל נכשל ב-`TryParse` ונופל למסלול הטקסטואלי —
ואז אפסים מובילים שוב משנים, כלומר הנרמול מפסיק לעבוד בדיוק במקרה שבו
הוא הכי נחוץ. שלישית, פורמט עשרוני אירופי אינו מפורסר.

**למה זה חשוב:** שתי הראשונות הן שקטות. עמודת סכום ב-`NUMBER(38,15)`
תסתיר פערים אמיתיים, ומזהה ארוך יסבול מכל בעיית האפסים המובילים למרות
שיש קוד שנועד לפתור אותה בדיוק.

**תיקון:** להשתמש ב-`System.Numerics.BigInteger` למספרים שלמים ארוכים,
או להשוות מספרית בלי לעבור דרך מחרוזת. עבור השברים — לקבוע את מספר
הספרות לפי ה-scale של העמודה מ-`GetColumnsWithTypesAsync` במקום קבוע
של עשר, או להשוות `decimal` ל-`decimal` ישירות.

## 11. במפתח כפול מושווית רק השורה הראשונה

**מקריאת קוד** — `CompareService.cs:1384-1392`:

```csharp
if (sqlKeyCounts.ContainsKey(compositeKey)) { sqlKeyCounts[compositeKey]++; }
else { sqlKeyCounts[compositeKey] = 1; sqlDataFiltered[compositeKey] = row; }
```

**מה קורה:** הספירה מטפלת בכפילויות נכון ומדווחת עליהן. אבל
`sqlDataFiltered` שומר רק את השורה **הראשונה** לכל מפתח, ומנוע השוואת
הערכים עובד מולו.

**למה זה חשוב:** אם מפתח מופיע פעמיים עם ערכים שונים, ההבדל בשורה
השנייה אינו מושווה כלל. הכפילות כן תדווח, כך שהמשתמש יקבל רמז — אבל
הוא לא יראה שהערכים בשורה שלא נבדקה שונים.

**תיקון:** לפחות להוסיף אזהרה מפורשת בדוח שערכי השורות הכפולות לא
הושוו. אם נדרשת השוואה מלאה — להחזיק `List<row>` לכל מפתח ולהשוות
זוגות לפי סדר.

## 12. סדר המיון עשוי להיות שונה בין SQL Server לאורקל

**מקריאת קוד** — `CompareService.cs:985-993`. זו הסקה שלא הרצתי, ונדרש
מסד נתונים אמיתי כדי לאמת אותה.

**מה קורה:** יש `ORDER BY` על שדות המפתח לפני `TOP`/`FETCH FIRST`, עם
הערה שמסבירה נכון למה. אבל ה-`ORDER BY` מבוצע בכל צד לפי כללי המיון
של אותו מסד — SQL Server לפי ה-collation של העמודה, אורקל לפי
`NLS_SORT` שברירת המחדל שלו היא מיון בינארי.

**למה זה חשוב:** עבור מפתח **מספרי** אין בעיה. עבור מפתח **טקסטואלי**
שני הצדדים עשויים למיין אחרת — למשל ביחס לאותיות גדולות וקטנות, לרווחים,
או לסדר האותיות העבריות. עם `maxRows` של 1000, שני הצדדים יחזירו חלונות
של 1000 שורות **שונות**, וכל הפרש ביניהן ידווח כשורה חסרה. זה בדיוק
הכשל שה-`ORDER BY` נועד למנוע, רק ברמה אחת עמוקה יותר.

**תיקון:** כשיש `maxRows` ומפתח טקסטואלי — למיין לפי ביטוי שמתנהג זהה
בשני הצדדים, למשל `ORDER BY UPPER(col)` בשני הצדדים, או `NLSSORT` באורקל
כדי ליישר את הכללים. פשוט יותר: להזהיר במסך שהגבלת השורות עם מפתח
טקסטואלי אינה מבטיחה חלון זהה, ולהמליץ להשוות ללא הגבלה או עם סינון
טווח מפתחות מפורש במקום `TOP`.

## 13. קובץ אקסל עם כותרות וללא שורות נתונים מדווח כחסר עמודות

**מקריאת קוד** — `CsvParser.cs:92-96`: `GetHeaders` שולף את הכותרות
מ-`MiniExcel.Query(...).FirstOrDefault()`, כלומר ממפתחות המילון של שורת
הנתונים **הראשונה**. בקובץ שיש בו כותרות בלבד, `FirstOrDefault()` מחזיר
null והפונקציה מחזירה רשימה ריקה. הקורא ב-`CompareController.cs:616`
מתרגם את זה להודעה "לא נמצאו עמודות או כותרות באחד הקבצים".

**למה זה חשוב:** ההודעה מטעה — יש כותרות, אין שורות. וזה מקרה לגיטימי:
השוואה של קובץ יעד ריק מול מקור מאוכלס היא בדיוק מה שרוצים לבדוק בתחילת
מיגרציה, ובמצב הזה אי אפשר בכלל להגיע למסך המיפוי.

**תיקון:** לקרוא את הכותרות עם `useHeaderRow: false` ולקחת את השורה
הראשונה, או להבדיל בהודעה בין "אין כותרות" ל"אין שורות נתונים".

## 14. החלטות עסקיות שאינן באגים

אלה לא תקלות אלא בחירות שכדאי שיהיו מודעות ומתועדות, ורצוי שיהיו ניתנות
לשליטה מהמסך:

**אפס נחשב ריק.** `IsEmptyOrZero` (`CompareService.cs:1856`) מחזיר true
עבור `"0"`. כלומר עמודה שבמקור יש בה `0` ובמסד היעד היא `NULL` נחשבת
תואמת. במיגרציה זה יכול להסתיר פער אמיתי — `0` ו"אין נתון" אינם אותו
דבר בשדה סכום. שווה לוודא שזו הכוונה, ולהפוך לאפשרות. הערה נוספת:
הענפים `"0.0"` ו-`"0.00"` באותה פונקציה הם קוד מת עבור ערכים שעברו
`NormalizeTypedValue` עם `"Number"`, שכן שם אפס תמיד יוצא `"0"`.

**רגישות לאותיות גדולות וקטנות.** `"abc"` ו-`"ABC"` מדווחים כשונים,
בעוד ש-collation ברירת המחדל של SQL Server מחשיב אותם כזהים. כלומר
הכלי מדווח פער שמסד הנתונים עצמו אינו רואה. שווה מתג "התעלם מרישיות".

**רווחים בתוך הערך.** `"A B"` ו-`"A  B"` שונים. `Trim()` מטפל בקצוות
בלבד. שווה מתג "כווץ רווחים פנימיים", שימושי במיוחד בשמות ובכתובות.
